## iOS 1.0.2 — AdMob SKAdNetwork fix + automatic in-app update prompt
User reported ads not showing on the live iOS build. Root cause: `react-native-google-mobile-ads`'s Expo config plugin supports a `skAdNetworkItems` option to populate `SKAdNetworkItems` in Info.plist (required by iOS 14+ for ad network attribution — without it, most demand partners won't bid, causing low/no fill), but it was never set. Fixed by adding Google's standard list of ~40 SKAdNetwork identifiers to the plugin config in `app.json`.

Also built a new feature per user request: an in-app "Update Available" popup (`components/UpdatePrompt.js`) shown on launch when a newer version exists than the one installed, so existing users don't need to be told individually to update. First implementation used a Firestore `appConfig/version` doc requiring a manual update after every release — user asked if this could be fully automatic instead. Refactored `utils/appUpdateCheck.js` to query the **live store versions directly**: Apple's public iTunes Lookup API (`itunes.apple.com/lookup?id=...`, official, no credentials needed) for iOS, and a regex extraction from the public Play Store listing HTML for Android (no official free API exists; verified the exact pattern works against the real live listing before shipping). No manual step ever needed now — whatever is actually live on each store is what gets compared against. "Update Now" opens the platform's store app directly (`market://` / `itms-apps://` schemes, not just a browser link).

Since `app.json`'s shared `version` field had already reached "1.0.1" (approved/live), and Apple requires every new binary's version to exceed the last *approved* one, bumped to **1.0.2** for this build. Built and submitted as iOS version 1.0.2, build 7 (an earlier build 6 was superseded before submission so the update-check refactor could ship in the same binary rather than needing a separate OTA/runtime-version-mismatch workaround). Waiting on Apple processing, then needs the usual manual "attach build to version → Add for Review" step in App Store Connect.

Note: the update-prompt feature will only start working for Android once a *new* Android build is shipped (the current live Android build predates this feature entirely).

Fixed by:

Verified live via `curl` (200 OK, exact content match, http correctly redirects to https).
- **iOS**: found "Marketing URL" is a per-version field (on the version's own page, not the separate "App Information" page) and was **grayed out/uneditable** because version 1.0.2 was already live — Apple locks metadata fields on released versions. Fixed by bumping to version **1.0.3** (build 8, `app.json` + rebuild + `eas submit`), which unlocked a fresh editable version where Marketing URL was set to `https://hassanshafique2001-cmd.github.io`. ## Ledger: independent reminder date/time, on both "new contact" and "known contact" add-transaction flows
User wanted the Ledger tab's own "+" (adding a brand-new contact) to also get a "Set Reminder" toggle like the contact-detail one already had - but with a twist: when turned on, the reminder needs its **own** date+time, separate from the transaction's date+time (e.g. record a transaction today but want a recurring reminder on the 1st of every month, not tied to today's date).

- **`utils/notifications.js`**: added `scheduleLedgerReminder(payment)` - a second scheduler alongside the existing bill-only `schedulePaymentReminder`. Takes an explicit `payment.reminderDate` (full date+time, no "fixed 9 AM" rule like bills have) and schedules either a one-time `DATE` trigger, or - if "Repeat Monthly" is on - a native `MONTHLY` trigger (`{ type: MONTHLY, day, hour, minute }`, newly discovered available in the installed `expo-notifications` version). This is a real OS-level repeating notification, unlike bills' "Repeat Monthly" which only works by manually rescheduling when a payment gets marked paid - ledger transactions have no such action anymore, so a true recurring trigger was the only way to make monthly ledger reminders actually fire more than once.
- **`app/add-payment.js`**: new `reminderDate` state (separate `DateTimePicker`s for date and time, mirroring the existing transaction-date pattern but fully independent), defaulting to "now" same as the transaction date.
